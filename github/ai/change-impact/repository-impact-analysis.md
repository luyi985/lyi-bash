# Project Change Impact Analyzer

## Objective

Map dependency-level or change-level facts to actual project usage. Determine which changes are applicable, trace their runtime and business effects, evaluate risk, and produce an evidence-backed verification and release recommendation.

## Inputs

Use one or more of:

- a `change-manifest.yaml` generated by a version diff analyzer
- a Git diff, pull request diff, commit range, patch, or changed file list
- repository source code
- package and lock files
- runtime and deployment configuration
- tests, mocks, fixtures, CI, monitoring, and runbooks
- architecture or data-flow documentation

If no Change Manifest exists, derive a provisional change list and label it provisional. Do not silently invent before-state behavior.

## Workflow

1. Establish scope and baseline.
   - Identify repository root, workspace boundaries, changed component, before state, after state, deployment target, and runtime version.
   - Record unavailable inputs.

2. Validate the supplied Change Manifest.
   - Confirm dependency name and versions against project files when possible.
   - Detect conflicts between manifest claims and installed declarations, metadata, or source.
   - Return context conflicts rather than forcing an impact conclusion.

3. Build a reference and dependency map.
   Search beyond direct imports:
   - imports, require, dynamic import, re-exports
   - wrappers, adapters, factories, dependency injection, framework modules
   - configuration, environment variables, defaults, schemas
   - type-only references and generated code
   - tests, mocks, fixtures, build and deployment scripts
   - package exports, plugins, reflection, string-based registration, runtime loading

4. Trace reachable paths.
   For each candidate change, build:

```text
Change
→ direct use or wrapper
→ internal component
→ downstream service, topic, queue, database, API, or user flow
→ technical observable
→ business consequence
```

Do not report a path as confirmed unless each material hop has evidence.

5. Evaluate trigger conditions for every change.
   Assign one applicability status:
   - `applicable`
   - `not-applicable`
   - `conditionally-applicable`
   - `unknown`
   - `context-conflict`

6. Compare effective behavior.
   Check whether the project overrides defaults, transforms return values, catches errors, normalizes data, implements idempotency, retries independently, or isolates the library behind an adapter.

7. Assess impact dimensions.
   - compile and type impact
   - runtime behavior
   - errors and recovery
   - data and schema compatibility
   - concurrency, ordering, retry, timeout, and duplication
   - performance and capacity
   - lifecycle and resource cleanup
   - security and supply chain
   - logs, metrics, tracing, alerting
   - deployment, mixed-version operation, and rollback
   - user or business outcomes

8. Assess test quality, not only test existence.
   Detect:
   - mocks that preserve old behavior
   - tests that bypass the changed dependency
   - compile-only assurance
   - missing failure, concurrency, lifecycle, and integration coverage
   - tests that do not use the resolved new version

9. Score risk using `./risk-assessment-model.md`.
   Keep evidence confidence separate from risk severity.

10. Create a verification plan.
    Map every medium, high, or critical risk to a concrete test, runtime check, rollout guard, or rollback action.

11. Produce a release recommendation:
    - `safe-to-merge`
    - `merge-with-required-tests`
    - `deploy-behind-feature-flag`
    - `canary-required`
    - `manual-migration-required`
    - `do-not-deploy`
    - `insufficient-evidence`

12. Validate the final report data with:

```bash
python .github/ai/change-impact/scripts/validate_impact_report.py impact-report.yaml
```

## Evidence discipline

Label findings as:

- `confirmed`: directly supported by project and change evidence
- `likely`: strong causal path with one non-critical uncertainty
- `possible`: plausible but missing material runtime or configuration evidence
- `unknown`: insufficient evidence
- `not-impacted`: trigger condition is demonstrably false

Rules:

- Finding an import proves usage, not impact.
- Not finding an import does not prove no impact.
- A passing build does not prove behavioral compatibility.
- Passing unit tests do not prove runtime compatibility.
- A mocked dependency may create false confidence.
- Do not fabricate test execution, metrics, traffic, or production behavior.
- Keep technical impact distinct from business impact.
- Preserve `not-applicable` changes with evidence so reviewers can see what was checked.
- Treat dynamic loading and reflection as unknown unless resolved.
- Never modify source, migrations, or production configuration unless explicitly requested.

## Output contract

Produce both `impact-report.yaml` and a reviewer-friendly Markdown report with:

1. change and project baseline
2. evidence reviewed and missing
3. applicability matrix for all change IDs
4. confirmed impact paths
5. likely, possible, unknown, and not-impacted findings
6. affected components and owners when known
7. runtime and business impact
8. test and observability gaps
9. deployment, mixed-version, and rollback analysis
10. risk register
11. required verification
12. blocking and non-blocking actions
13. release recommendation
14. confidence level and unresolved questions

Use `./impact-report-schema.md` and `./risk-assessment-model.md` as authoritative formats.
